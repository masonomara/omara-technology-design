# Findings — YYYY-MM-DD

Site: [url] · Cycle: [YYYY-MM-DD] · Generated by `hobbes/tools/evaluation.py` from `raw/`.

This is the problem catalog. Dense, deterministic, written for an agent. It sits between two documents and is neither of them:

- `01-baseline.md` is the scorecard. The numbers, for a stakeholder. Findings is the evidence. Every problem, fully specified, for an agent.
- `03-plan.md`, the next stage, groups these findings into systems, proposes one fix per system, and rates effort and impact against `MISSION.md`. Findings does none of that. Its one job is to hand the plan everything it needs and invent nothing.

## How this is built, and why it repeats

`evaluation.py` reads the cycle's raw files (`raw/*.psi.json`, `raw/*.seo.json`, `raw/crawl.json`) and pulls out every problem verbatim. No judgment. No prose written fresh each run. Every list is sorted by a stable key, so the same raw gives the same findings, IDs and all. Run it as often as you like. The document does not drift.

Total coverage, by construction. Every failing check in the raw becomes a finding. No shortlist, no hand-picked IDs, no mission weighting that decides what is worth showing. Performance audits come straight from the Lighthouse category, with Lighthouse's own title and description as the explainer. So when the tool renames an audit, as it renamed most opportunities to the `*-insight` family, nothing slips through a hardcoded match. Where a list is capped for length, the cap is stated (`+N more`). Where an audit has no clean resource list, its Lighthouse `displayValue` stands in as evidence and the finding still appears. Coverage is never dropped in silence. How much evidence a finding carries depends on what the raw exposes. Whether it appears at all does not — every failure becomes a finding.

What is not deterministic is not here:

- The fix. Which file, which line, which approach. That goes to the plan.
- Effort and impact. How long, what it needs, how far it moves the mission. The plan.
- Root cause in our source. The evidence points at a component, a selector, a class, a snippet. Naming the source file and finding the real cause is the plan's work.

Findings gives the what, the where it shows, and the how it works. The plan decides what to do about it.

## How to read a finding

Every finding is one block, the same shape every time:

```
### <DOMAIN>-<n> · <short title>
- **What / why:** <static explainer — what this rule/metric is, why it matters, where it usually lives in the codebase>
- **Source:** <tool> · <audit / table id>
- **Target → measured:** <the BASELINE.md target> → <the measured value> (**gap**)
- **Scope:** golden path: <pages/devices affected> · sitewide: <count> / <pages crawled>
- **Evidence:** (verbatim from raw)
  - <selector / snippet / url / bytes / ms / heading tree>
  - … (+N more)
```

- Domains run in a fixed order: `A11Y`, `SEO`, `PERF`, `SEC`, `BP`. This is reading order, not priority. Findings does not weigh impact. That is the plan's job, rated against `MISSION.md`. The order is fixed only so IDs don't move between cycles.
- IDs are stable within a cycle (`A11Y-1`, `SEO-3`, …). Quote them in the plan.
- Scope separates the golden path, the locked pages measured deep by PSI and seo, from sitewide, every page measured broad by the crawl. A problem on both is worse than a problem on either.
- Evidence is raw. A selector is the real DOM selector. A snippet is the real HTML. The bytes and milliseconds are the real numbers. Trust them, and open `raw/` (say `raw/crawl.json`) to go deeper.

## Sections

1. A11Y, accessibility. Golden-path axe failures from PSI, grouped per rule with node counts and sample selectors. Then sitewide a11y from the crawl's element-level counts (critical and warning), not a blunt one-flag-per-page total.
2. SEO, search and discoverability. Golden-path checklist failures with specifics. Then sitewide: missing meta descriptions (the full list), duplicate titles, duplicate meta descriptions, heading-structure errors, Open Graph coverage, broken links.
3. PERF, performance. Per page and device, the scores and lab metrics, with the field (CrUX) verdict alongside for context. Then every failing performance audit from the Lighthouse category: render-blocking, image delivery, cache lifetimes, JS bootup, main-thread work, byte weight, unused or legacy or unminified or duplicated JS and CSS, unsized images, forced reflow, LCP discovery, layout-shift culprits, network chains. Each one carries the real resources behind it. Then the crawl's slowest URLs sitewide.
4. SEC, security. Missing or weak response headers with the crawler's recommendation, plus CORS, compression, TLS.
5. BP, best practices and structure. PSI best-practice failures (console errors, deprecations, and so on) and the crawl's structural table (invalid, duplicate, or oversized inline SVG, non-clickable phone numbers, DOM depth), row by row. Some checks the crawl files under best practices belong to another domain: heading structure, title and description uniqueness, Brotli. Those are reported in their home section, not repeated here.

A domain with no failures prints one line, `— all checks pass`, and no blocks.

## Pointers

- `01-baseline.md` — the scorecard for this cycle, the numbers these findings detail.
- `raw/` — the source every finding is pulled from (`raw/crawl.json` is SiteOne's full whole-site crawl).
- `MISSION.md` — the priorities the plan rates impact against.
